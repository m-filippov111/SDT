# Лекция 1. Введение в жизненный цикл ПО и управление проектами

## 1. Модели жизненного цикла программного обеспечения

### 1.1. Каскадная модель (Waterfall)

Классическая модель разработки, где этапы выполняются последовательно:

```
Требования → Проектирование → Реализация → Тестирование → Эксплуатация
```

**Особенности:**

- Каждый этап завершается полностью перед началом следующего
- Чёткое документирование на каждом этапе
- Сложно возвращаться к предыдущим этапам

**Недостатки:**

- Ошибки обнаруживаются поздно (Закон Боэма: чем быстрее мы обнаруживаем ошибки, тем эффективнее мы разрабатываем ПО)
- Сложно адаптироваться к изменениям требований
- Заказчик видит результат только в конце

### 1.2. Спиральная модель

Итеративная модель, сочетающая элементы каскадной модели и прототипирования.

**Циклы спирали:**

1. Определение целей
2. Оценка рисков
3. Разработка и тестирование
4. Планирование следующей итерации

**Преимущества:**

- Учёт рисков на каждом этапе
- Возможность возврата на предыдущие этапы
- Гибкость в управлении требованиями

### 1.3. Инкрементная модель

Продукт разрабатывается и поставляется частями (инкрементами), каждый из которых добавляет новую функциональность.

**Принцип:**

```
Инкремент 1 → Инкремент 2 → Инкремент 3 → ... → Готовый продукт
```

**Преимущества:**

- Ранняя поставка части функциональности
- Обратная связь от заказчика на ранних этапах
- Снижение рисков

### 1.4. Гибкая разработка (Agile)

**Agile Манифест (2001):**

> Люди и взаимодействие важнее процессов и инструментов
> Работающий продукт важнее исчерпывающей документации
> Сотрудничество с заказчиком важнее согласования условий контракта
> Готовность к изменениям важнее следования первоначальному плану

**12 принципов Agile:**

1. Наивысший приоритет — удовлетворение заказчика через частые поставки ценного ПО
2. Изменения в требованиях приветствуются даже на поздних этапах
3. Работающий продукт выпускается каждые несколько недель или месяцев
4. Наиболее эффективный способ передачи информации — личное общение
5. Бизнес и разработчики работают вместе ежедневно
6. Проекты строятся вокруг мотивированных людей
7. Работающее ПО — главная мера прогресса
8. Постоянная скорость разработки (устойчивый темп)
9. Постоянное внимание к техническому совершенству
10. Простота — искусство не делать лишней работы
11. Лучшие решения создаются в самоорганизующихся командах
12. Команда постоянно ищет способы стать эффективнее

> **Закон Галла:** Любая работающая сложная система развивается на базе работающей простой системы.

> **MVP (Minimum Viable Product):** Старт разработки с минимально жизнеспособного продукта позволяет быстро протестировать идею.

### 1.5. Сравнение моделей

| Модель       | Гибкость      | Риски       | Подходит для                       |
| ------------ | ------------- | ----------- | ---------------------------------- |
| Каскадная    | Низкая        | Высокие     | Стабильные требования              |
| Спиральная   | Средняя       | Управляемые | Сложные проекты с рисками          |
| Инкрементная | Высокая       | Средние     | Проекты с поэтапной поставкой      |
| Agile        | Очень высокая | Низкие      | Проекты с меняющимися требованиями |

## 2. Методологии гибкой разработки

### 2.1. Scrum

**Кен Швабер, конец 90-х**

**Ключевые понятия:**

- **Спринт** — ограниченная по времени итерация (обычно 2–4 недели)
- **Бэклог** — набор задач, которые должны быть сделаны
- **Бэклог спринта** — задачи, запланированные на текущий спринт

**Роли:**

- **Product Owner** — отвечает за бэклог, приоритеты, ценность продукта
- **Scrum Master** — фасилитатор, устраняет препятствия, следит за процессами
- **Development Team** — разработчики, выполняющие задачи

**Процесс:**

```
Планирование спринта (8 ч)
↓
Ежедневные планерки (15 мин) - Что делал? Что буду делать? Что мешает?
↓
Спринт-ревью (демонстрация результатов)
↓
Ретроспектива (3 ч) - что было хорошо, что улучшить
↓
Планирование следующего спринта
```

**Scrum-доска:** To Do → In Progress → Review → Done

### 2.2. Kanban

**Основа:**

- Ограничение количества задач в очереди (WIP — Work In Progress)
- Оставшиеся без задач помогают отстающим
- Непрерывный поток, без фиксированных итераций

**Область применения:**

- Большое количество однотипных задач
- Большая взаимозаменяемость сотрудников
- Отсутствие фиксированных сроков
- Техническая поддержка, работа с клиентами, системное администрирование

**Kanban vs Scrum:**

| Характеристика | Scrum                   | Kanban                |
| -------------- | ----------------------- | --------------------- |
| Итерации       | Фиксированные спринты   | Непрерывный поток     |
| Роли           | Чётко определены        | Не обязательны        |
| Планирование   | В начале спринта        | По мере необходимости |
| Изменения      | Только в начале спринта | В любой момент        |
| Метрики        | Velocity                | Lead Time, Cycle Time |

### 2.3. Extreme Programming (XP)

**Кент Бек, конец 90-х**

**12 практик XP:**

1. Парное программирование
2. Игра в планирование
3. TDD (Test Driven Development)
4. Заказчик как член команды
5. Непрерывная интеграция
6. Рефакторинг
7. Частые релизы
8. Стандарты кодирования
9. Коллективное владение кодом
10. Простая архитектура
11. Метафора системы
12. Постоянная скорость

### 2.4. Lean

**Модификация Toyota Production System для разработки ПО**

**7 принципов Lean:**

1. Eliminate waste (устранить потери)
2. Amplify learning (усилить обучение)
3. Decide as late as possible (принимать решения как можно позже)
4. Deliver as fast as possible (доставлять как можно быстрее)
5. Empower the team (дать полномочия команде)
6. Build integrity in (встраивать целостность)
7. See the whole (видеть целое)

## 3. Управление проектами

### 3.1. Планирование

**Диаграмма Гантта**

- Визуальное отображение задач во времени
- Отношения между задачами: start-to-start, finish-to-start, finish-to-finish
- Простота и наглядность

**Метод критического пути**

- Определение задач, влияющих на общую длительность проекта
- Фокус на критических задачах

### 3.2. Оценка трудоёмкости

**Проблемы оценок:**

- Учесть все задачи и зависимости
- Учесть риски
- Недостаток информации
- Ограниченное время

**Методы оценки:**

- **Метод подобия** — на основе опыта похожих проектов
- **Разделяй и властвуй** — декомпозиция до оцениваемых частей
- **Оценки в диапазоне** — N ± M часов (M показывает точность)

### 3.3. PERT (Project Evaluation and Review Technique)

**Разработан в 1958 году для проекта Polaris.**

**Формула:**

```

Оценка = (Оптимистичная + 4 × Реалистичная + Пессимистичная) / 6

```

**Физический смысл:**

- SD = (P - O) / 6 — показывает величину риска
- Проект ET = Сумма(ET) — общая оценка
- Проект SD = √(Сумма(V)) — общий риск

### 3.4. Планирование покер (Planning Poker)

Метод коллективной оценки, где каждый участник:

1. Получает колоду карт с числами (Фибоначчи: 1, 2, 3, 5, 8, 13, 21)
2. Обсуждает задачу
3. Одновременно показывает оценку
4. Если оценки различаются — обсуждают и повторяют

**Социальные аспекты:**

- У разных людей разная систематическая погрешность
- Люди склонны соглашаться с мнением большинства (эксперимент Аша)

## 4. Законы и принципы разработки ПО

### Закон Брукса

> «Чтобы родить ребенка требуется девять месяцев независимо от того, сколько женщин привлечено к решению данной задачи.»

> **Следствие:** Если проект не укладывается в сроки, то добавление рабочей силы задержит его ещё больше.

### Закон Боэма

> Чем быстрее мы обнаруживаем ошибки, тем эффективнее мы разрабатываем ПО.

### Закон Галла

> Любая работающая сложная система развивается на базе работающей простой системы. Сложные системы, созданные с нуля, никогда не будут работать в реальном мире.

## 5. Понятие DevOps

**DevOps** — набор практик, позволяющих достигать бизнес-целей через активное взаимодействие разработки и эксплуатации.

**CAMs (4 pillars):**

- **Culture** — люди и процессы на первом месте
- **Automation** — инфраструктура как код, версионирование
- **Measure** — доступ к логам и метрикам
- **Share** — обратная связь между разработчиками и операторами

### Continuous Integration Maturity Model

| Уровень                    | Описание                                        |
| -------------------------- | ----------------------------------------------- |
| **Initial**                | Процессы непредсказуемые, VCS, ночные сборки    |
| **Managed**                | Build on commit, auto deploy to dev, unit tests |
| **Defined**                | Auto deploy on test, on demand deploy to prod   |
| **Quantitatively Managed** | Auto functional tests, auto deploy to prod      |
| **Optimizing**             | Continuous deploy to prod                       |
