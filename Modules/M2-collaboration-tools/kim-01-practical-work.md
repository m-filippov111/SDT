# КИМ-2.1. Командные модели работы с репозиторием

## 1. Назначение

Проверить сформированность индикатора **PL-1.1** (уровень С): способность разрабатывать, отлаживать и тестировать прикладные решения с использованием Python, включая практики коллективной работы с системой контроля версий, настройку CI/CD и автоматических проверок.

## 2. Проверяемые результаты обучения

| PL-1.1 | Разрабатывает и отлаживает прикладные решения разной сложности с использованием Python, тестирует, испытывает и оценивает их качество |    С    | Обучающийся способен эффективно использовать Git для командной разработки: применять модели ветвления, создавать и ревьюить Pull Request, разрешать конфликты, настраивать CI/CD и автоматические проверки |

## 4. Задание

### Этап 0. Подготовка репозитория

1. Создайте репозиторий на GitHub (приватный) для вашего командного проекта.
2. Добавьте всех участников команды в репозиторий с правами на запись.
3. Создайте файл `.gitignore` для Python (и Java, если используется).
4. Инициализируйте проект с базовой структурой:

```
team-XX-project/
├── .github/
│ └── workflows/
├── .gitignore
├── README.md
├── requirements.txt
├── setup.py
├── src/
│ ├── init.py
│ └── core/
│ └── init.py
└── tests/
├── init.py
└── test_core.py
```

### Этап 1. Выбор модели ветвления и настройка

Изучите основные модели ветвления в Git и выберите подходящую для вашего проекта:

- **Git Flow** — классическая модель (подходит для больших проектов с релизами)
- **GitHub Flow** — простая модель (подходит для непрерывной поставки)
- **Trunk-Based Development** — разработка в одной основной ветке (подходит для CI/CD)

**Результат:** Файл `docs/branching-model.md` с описанием выбранной модели и обоснованием.

### Этап 2. Настройка защиты веток

Настройте защиту основной ветки в GitHub/GitLab:

- Требование Pull Request перед слиянием
- Требование одобрения код-ревью (минимум 1 участник)
- Запрет прямых push в основную ветку
- Требование прохождения CI-проверок

**Результат:** Скриншот настроек защиты веток.

### Этап 3. Настройка CI/CD

Настройте автоматический CI-конвейер для вашего Python-проекта:

1. Создайте файл `.github/workflows/ci.yml` (для GitHub Actions).
2. Настройте следующие шаги:
   - Установка Python (версии 3.10 и 3.11)
   - Установка зависимостей из `requirements.txt`
   - Запуск линтера (ruff или flake8)
   - Запуск тестов (pytest с генерацией coverage)
   - Проверка типов (mypy, опционально)

**Результат:** Работающий CI-конвейер, который запускается при каждом push и Pull Request.

### Этап 4. Настройка Git Hooks с pre-commit

Установите и настройте `pre-commit` для автоматических проверок перед коммитом:

1. Установите `pre-commit`: `pip install pre-commit`
2. Создайте файл `.pre-commit-config.yaml` с хуками:
   - `trailing-whitespace` — удаление пробелов в конце строк
   - `end-of-file-fixer` — пустая строка в конце файла
   - `check-yaml` — проверка YAML-синтаксиса
   - `ruff` — линтер для Python
   - `pytest` — запуск тестов (опционально)

**Результат:** Работающий pre-commit, проверяющий код перед каждым коммитом.

### Этап 5. Создание шаблона Pull Request

Создайте шаблон Pull Request для репозитория:

**Результат:** Файл `.github/pull_request_template.md` с чеклистом проверки.

### Этап 6. Практика работы с ветками и Pull Request

Каждый участник команды выполняет следующее:

1. Создаёт feature-ветку с именем `feature/username/task-description`
2. Вносит изменения в код (добавляет функцию и тесты)
3. Создаёт Pull Request в основную ветку
4. Другой участник выполняет код-ревью
5. Вносятся исправления по замечаниям
6. Pull Request принимается и сливается

**Результат:** История репозитория с несколькими Pull Request от разных участников.

### Этап 7. Разрешение конфликтов

Создайте искусственную ситуацию конфликта и разрешите её:

1. Два участника одновременно изменяют один и тот же файл в разных ветках
2. Первый Pull Request принимается
3. Второй Pull Request обнаруживает конфликт
4. Конфликт разрешается локально с использованием `git mergetool` или IDE
5. Pull Request обновляется и принимается

**Результат:** Файл `docs/conflict-resolution.md` с описанием процесса разрешения конфликта.

### Этап 8. Дополнительно: CI/CD с несколькими ОС (опционально)

Настройте CI для запуска тестов на нескольких операционных системах:

- Ubuntu (Linux)
- Windows
- macOS

**Результат:** Расширенный `ci.yml` с матрицей ОС.

## 8. Методические рекомендации

### Для студентов

1. **Модель ветвления**: GitHub Flow проще для начала, Git Flow даёт больше контроля.
2. **CI/CD**: Начинайте с простого (запуск тестов), потом добавляйте линтер и проверку типов.
3. **Pre-commit**: Установите сначала базовые хуки, затем добавляйте специфичные для Python.
4. **Pull Request**: Держите PR небольшими — их проще ревьюить и сливать.
5. **Конфликты**: Не бойтесь конфликтов — это норма в командной разработке.

### Для преподавателей

1. Проверьте, что все участники активно создавали Pull Request и участвовали в ревью.
2. Оцените качество код-ревью — должно быть не формальное "LGTM", а содержательные комментарии.
3. Убедитесь, что CI действительно работает и проверяет код при каждом push.
4. Проверьте, что pre-commit настроен и работает на всех машинах команды.
