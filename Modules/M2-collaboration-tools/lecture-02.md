# Лекция 2. Инструменты коллективной разработки

## 1. Системы контроля версий (VCS)

### 1.1. Что такое VCS

**Version Control System** — система, позволяющая хранить несколько версий одного и того же файла, возвращаться к более ранним версиям, отслеживать изменения.

**Версия (ревизия)** — конкретное зафиксированное состояние репозитория.

**Преимущества Git:**

- Сохранение различных версий проекта
- Быстрый переход между версиями (откат)
- Улучшение процесса командной работы
- Независимая одновременная разработка различных функций

### 1.2. Эволюция VCS

| Поколение               | Примеры                | Особенности                                 |
| ----------------------- | ---------------------- | ------------------------------------------- |
| Локальные               | RCS, SCCS              | Один пользователь, локальные файлы          |
| Централизованные (CVCS) | CVS, SVN, Perforce     | Единый сервер, все изменения централизованы |
| Распределённые (DVCS)   | Git, Mercurial, Bazaar | Полная копия репозитория у каждого          |

### 1.3. Централизованные vs Распределённые

**Достоинства централизации:**

- Всегда есть "эталонная" версия кода
- Централизованное администрирование
- Привычный workflow

**Недостатки централизации:**

- Единая точка отказа — сервер
- Любые изменения влияют на всех пользователей
- Требуется гибкая система прав

**Достоинства DVCS (Git):**

- Нет выделенного центра (технически)
- Вся история дублируется в каждом локальном репозитории
- Нет необходимости в постоянном соединении
- Нет необходимости в управлении правами
- Поддерживает любой workflow
- Каждый разработчик работает в своей песочнице
- Локальные операции работают быстро

**Недостатки DVCS:**

- Всё ещё требуются бэкапы
- Нет сквозных номеров ревизий
- Достаточно сложны в использовании

### 1.4. Объекты Git

| Тип объекта       | Описание                                     |
| ----------------- | -------------------------------------------- |
| **Blob**          | Содержимое файлов (каждая версия)            |
| **Tree**          | Папки и имена файлов со ссылками на объекты  |
| **Commit**        | Tree + метаданные + родительские коммиты     |
| **Annotated Tag** | Метка с метаданными (автор, дата, сообщение) |

**Уникальный ID** — SHA-1 хэш (160 бит, 40 шестнадцатеричных символов)

### 1.5. Статусы файлов в Git

Untracked → Staged → Unmodified → Modified
↑ ↑
git add git add
↓ ↓
git commit edit

text

- **Untracked** — не отслеживаемый (только создан)
- **Staged** — подготовленный (после `git add`)
- **Unmodified** — не модифицированный (после `git commit`)
- **Modified** — модифицированный (отличается от версии в .git)
- **Ignored** — игнорируемый (в .gitignore)

### 1.6. Основные команды Git

**Настройка:**

```bash
git config --global user.name "Your Name"
git config --global user.email "your.email@example.com"
```

Инициализация и клонирование:

```bash
git init                          # создать репозиторий
git clone <url>                   # клонировать удалённый репозиторий
```

Работа с изменениями:

```bash
git status                        # текущее состояние
git add <files>                   # подготовить файлы к коммиту
git commit -m "message"           # создать коммит
git commit --amend                # изменить последний коммит
```

История:

```bash
git log                           # история коммитов
git log --oneline                 # сокращённый лог
git log --graph                   # граф коммитов
git shortlog                      # статистика по авторам
```

Перемещение:

```bash
git checkout <commit-hash>        # переход к определённому коммиту
git checkout <branch>             # переключение на ветку
```

Работа с объектами:

```bash
git cat-file -p <SHA-1>           # содержимое объекта
git cat-file -t <SHA-1>           # тип объекта
git rev-parse HEAD                # SHA-1 последнего коммита

```

### 1.7. Ветвление в Git

**Команды для работы с ветками:**

```bash
git branch <name> # создание ветки
git checkout <name> # переключение на ветку
git checkout -b <name> # создать и переключиться
git branch -d <name> # удалить ветку
git branch -m <new-name> # переименовать ветку
git branch -a # все ветки (включая удалённые)
git branch -vv # статус отслеживания
```

Слияние:

```bash
git merge <feature-branch> # слияние ветки в текущую
git merge --squash <branch> # объединить все коммиты в один

```

Пример ветвления:

```text

1. Создать новую ветку new-feature из ветки main
2. Перейти в new-feature
3. Внести изменения, создать коммиты
4. Перейти обратно в main
5. Выполнить слияние: git merge new-feature
6. Удалить ветку: git branch -d new-feature
```

**Git Flow — модель ветвления:**

- `master` — стабильная версия
- `develop` — ветка разработки
- `feature/*` — новые функции
- `release/*` — подготовка релиза
- `hotfix/*` — срочные исправления

**Упрощённый GitHub Flow:**

- `main` — стабильная версия
- `feature/*` — новые функции (от main)

### 1.8. Разрешение конфликтов

Конфликты возникают при слиянии, если один и тот же файл изменён в разных ветках.

**Процесс разрешения:**

1. Git отмечает конфликтующие участки в файле
2. Разработчик вручную выбирает, какой код оставить
3. После разрешения: `git add <file>` и `git commit`

**Инструменты:** IDE (VS Code, IntelliJ), `git mergetool`

### 1.9. Работа с удалённым репозиторием

**bash**

```
git remote add origin <url>       # подключить удалённый репозиторий
git remote -v                     # показать удалённые репозитории
git remote show origin            # информация о репозитории

git push origin <branch>          # отправить изменения
git push -u origin <branch>       # отправить + установить отслеживание

git pull origin <branch>          # загрузить и слить изменения
git fetch origin                  # загрузить изменения без слияния

git remote prune origin           # удалить устаревшие ссылки
```

**Процесс pull:**

1. `git fetch` — загрузка изменений
2. Обновление `FETCH_HEAD`
3. `git merge FETCH_HEAD` — слияние с текущей веткой

### 1.10. Работа с Pull Request

**Pull Request** — предложение о возможных изменениях, помогает разработчикам коммуницировать.

**Процесс:**

1. Создать локальную ветку для задачи
2. Внести изменения, создать коммиты
3. Отправить ветку на удалённый сервер (`git push`)
4. Создать Pull Request
5. Другой разработчик ревьюит код
6. Внести исправления по замечаниям
7. Одобрение и слияние
8. Закрытие PR и удаление ветки

**Forked repository** — копия репозитория в вашей учётной записи для:

- Внесения изменений в чужие проекты
- Экспериментов без риска повредить оригинальный код
- Контрибуции в Open Source

### 1.11. Продвинутые команды Git

**Rebase:**

```bash

git checkout feature
git rebase master # перенести коммиты feature поверх master
git checkout master
git merge feature # fast-forward слияние
Merge Rebase
```

| Merge              | Rebase                      |
| ------------------ | --------------------------- |
| Сохраняет историю  | Переписывает историю        |
| Запутанная история | Линейная история            |
| Безопаснее         | Опаснее для публичных веток |
| Простой процесс    | Требует осторожности        |

**Stash:**

**bash**

```
git stash                         # спрятать незакоммиченные изменения
git stash pop                     # восстановить изменения
```

**Reset:**

**bash**

```
git reset <commit>                # отменить коммит (изменения остаются)
git reset --soft <commit>         # отменить коммит (изменения в индексе)
git reset --hard <commit>         # полностью удалить коммит (ОПАСНО!)
git reset HEAD~5                  # сбросить 5 коммитов
```

**Revert:**

**bash**

```
git revert HEAD                   # создать коммит, отменяющий предыдущий
git revert <commit>               # отменить конкретный коммит
```

**Cherry-pick:**

**bash**

```
git cherry-pick <commit>          # перенести отдельный коммит
```

**Reflog (восстановление):**

**bash**

```
git reflog                        # показать все изменения HEAD
git checkout HEAD@{7}             # перейти к конкретному состоянию
```

**Garbage Collection:**

**bash**

```
git gc                            # очистка ненужных объектов
git gc --aggressive               # более глубокая очистка
```

### 1.12. Git Hooks

Git Hooks — механизм автоматического выполнения скриптов при определённых событиях.

**События хуков:**

- `pre-commit` — перед коммитом
- `commit-msg` — перед сохранением сообщения
- `post-commit` — после коммита
- `pre-push` — перед отправкой на сервер

**Использование:**

- Проверка и редактирование сообщения коммита
- Запуск тестов перед коммитом
- Проверка синтаксиса (ESLint, Pylint)
- Генерация уведомлений
- Автоматический деплой

**Pre-commit (Python):**

**yaml**

```
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.5.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-yaml
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.1.0
    hooks:
      - id: ruff
        args: [--fix]
```

### 1.13. .gitignore

Указывает Git, какие файлы и папки следует игнорировать.

**Что коммитить?**

- Исходный код
- Конфигурационные файлы (не содержащие секретов)
- `requirements.txt`, `pom.xml`, `package.json`

**Что не коммитить?**

- Папки сборки (`bin/`, `build/`, `target/`)
- Папки зависимостей (`node_modules/`)
- Скомпилированные файлы (`*.class`, `*.pyc`)
- Файлы логов (`*.log`)
- Скрытые файлы ОС (`.DS_Store`, `Thumbs.db`)
- Файлы с секретами (`.env`)

**Примеры:** [https://github.com/github/gitignore](https://github.com/github/gitignore)

## 2. Системы отслеживания ошибок (Bug Trackers)

### 2.1. Что такое баг

**Баг** — отклонение наблюдаемого результата от ожидаемого.

**Три условия бага:**

1. Известен ожидаемый результат
2. Известен фактический результат
3. Второе не соответствует первому

> "Это не баг, а фича!" — классическая шутка разработчиков

### 2.2. Зачем отслеживать баги

- Контроль состояния проекта
- Управление (что и в каком порядке делать)
- Оптимизация (сокращение издержек)
- Обеспечение качества (Quality Assurance)
- Возможность передавать задачи между участниками
- Сбор метрик о состоянии проекта
- Регрессионное тестирование

> **Не записано — не наблюдалось.**

### 2.3. Свойства багов

**Описание:**

1. Что нужно сделать для воспроизведения
2. Какое поведение наблюдается
3. Какое поведение ожидается
4. Workaround (способ обойти баг)

**Severity (Серьёзность):**

| Уровень      | Описание                                    |
| ------------ | ------------------------------------------- |
| **Blocker**  | Невозможно использовать продукт             |
| **Critical** | Ключевая функция не работает                |
| **Major**    | Обычная функция не работает                 |
| **Normal**   | Часть функциональности работает неправильно |
| **Minor**    | Недостатки в поведении                      |
| **Trivial**  | Опечатки, look & feel                       |

**Priority (Приоритет):**

- Выставляется менеджером (не тестировщиком!)
- Обычно числовая шкала 1–5 или 1–10

**Resolution:**

- **Fixed** — исправлен
- **Duplicate** — дубликат существующего
- **Wontfix** — не будет исправлен
- **Invalid** — не является багом
- **Works for me** — не воспроизводится

### 2.4. Жизненный цикл бага

**text**

```
New → Assigned → In Progress → Resolved → Verified → Closed
  ↑                                                    ↓
  └────────────────────────────────────────────────────┘
                      (Reopened)
```

### 2.5. Популярные Bug Trackers

| Название          | Тип          | Особенности                |
| ----------------- | ------------ | -------------------------- |
| **JIRA**          | Коммерческий | Мощный, гибкий, интеграции |
| **YouTrack**      | Коммерческий | От JetBrains, удобный      |
| **Redmine**       | Open Source  | Простой, гибкий            |
| **Bugzilla**      | Open Source  | Зрелый, проверенный        |
| **Trello**        | Коммерческий | Kanban-доски, простой      |
| **GitHub Issues** | Open Source  | Интеграция с Git           |

### 2.6. Метрики

**Полезные метрики:**

- Создано / закрыто (created/resolved)
- Среднее время решения (avg. resolution time)
- Средний возраст открытых багов (avg. age)
- Количество reopen'ов
- Пропущенные ошибки (escaped defects)

> **Важно:** Абсолютные значения метрик практически бесполезны. Информативно только изменение метрик внутри одной команды.

### 2.7. SMART-критерии для задач

- **S**pecific (конкретная)
- **M**easurable (измеримая)
- **A**chievable (достижимая)
- **R**elevant (актуальная)
- **T**ime-related (ограниченная во времени)

## 3. Сборка и Continuous Integration

### 3.1. Что такое сборка

**Сборка (build)** — процесс преобразования исходного кода в исполняемые артефакты.

**Артефакты:**

- Исполняемые файлы
- Документация
- JAR/WAR (Java)
- APK (Android)
- IPA (iOS)
- Инсталляторы Windows
- DEB/RPM пакеты (Linux)
- Прошивки устройств

**Задачи сборки:**

- Компиляция
- Генерация документации
- Сборка исполняемого файла
- Сборка инсталлятора
- Упаковка ресурсов
- Препроцессинг (SASS, LESS, CoffeeScript)
- Разрешение зависимостей
- Прогон unit-тестов
- Публикация результатов

### 3.2. Требования к системе сборки

- **Повторяемость** — проект собирается одним способом у всех участников
- **Простота** — новые участники собирают проект с минимумом затрат
- **Управление зависимостями**
- **Запуск автоматических тестов**

### 3.3. Эволюция систем сборки

| Поколение     | Примеры                        | Особенности                                             |
| ------------- | ------------------------------ | ------------------------------------------------------- |
| 1-е поколение | Make (1977)                    | Простые правила, нет управления зависимостями           |
| 2-е поколение | Autotools (2000), CMake (2000) | Генерация Makefile, кроссплатформенность                |
| 3-е поколение | Ant (199x)                     | XML, Java-экосистема                                    |
| 4-е поколение | Maven (2004)                   | Convention over configuration, управление зависимостями |
| Современные   | Gradle (2008), SBT             | Groovy/Scala DSL, гибкость                              |

### 3.4. Make

**makefile**

```
CC = gcc
CFLAGS = -g

all: helloworld

helloworld: helloworld.o
    $(CC) $(LDFLAGS) -o $@ helloworld.o

helloworld.o: helloworld.c
    $(CC) $(CFLAGS) -c -o $@ helloworld.c

clean:
    rm -f helloworld helloworld.o
```

**Недостатки:**

- Makefile становится очень большим
- Сложно читать
- Нет управления зависимостями
- Нет инкрементарной компиляции

### 3.5. CMake

**cmake**

```
cmake_minimum_required (VERSION 2.6)
project (Tutorial)
add_executable(hello hello.c)
```

**Особенности:** препроцессор для Make, кроссплатформенный

### 3.6. Maven

**Convention over Configuration:**

**text**

```
src/
  main/
    java/      # исходники
    resources/ # ресурсы
    webapp/    # веб-ресурсы
  test/
    java/      # тесты
    resources/ # тестовые ресурсы
pom.xml
```

**pom.xml:**

**xml**

```
<project>
    <modelVersion>4.0.0</modelVersion>
    <groupId>ru.nsu.fit</groupId>
    <artifactId>hello-world</artifactId>
    <version>1.0-SNAPSHOT</version>
    <packaging>jar</packaging>

    <dependencies>
        <dependency>
            <groupId>junit</groupId>
            <artifactId>junit</artifactId>
            <version>4.8.2</version>
            <scope>test</scope>
        </dependency>
    </dependencies>
</project>
```

**Управление зависимостями:**

- Кэш → локальный репозиторий → центральный репозиторий
- [http://search.maven.org](http://search.maven.org/)

**Недостатки:**

- Плохо кастомизируется
- Всё за пределами стандартного workflow настраивается сложно
- Провоцирует неряшливое управление зависимостями

### 3.7. Gradle

**groovy**

```
apply plugin: 'java'
apply plugin: 'maven'

dependencies {
    compile "org.slf4j:slf4j-api:1.7.12"
    compile "com.google.guava:guava:18.0"
    testCompile "junit:junit:4.12"
}

repositories {
    mavenCentral()
}
```

**Преимущества:** компактная запись, расширяемый build script
**Недостатки:** долгий старт, сложность

### 3.8. Управление зависимостями

**Проблема:** Большинство проектов использует сторонние библиотеки, которые зависят от других библиотек.

**Решения:**

1. Оставить на откуп желающим собрать проект
2. Хранить зависимости в VCS
3. Использовать универсальное хранилище (FTP, HTTP)
4. Использовать специализированное хранилище (Artifactory)

### 3.9. Continuous Integration (CI)

**CI** — практика непрерывной интеграции, при которой изменения кода автоматически собираются и тестируются.

**Что даёт CI:**

- Эталонная среда сборки
- Раннее обнаружение проблем интеграции
- Постоянное наличие текущей версии продукта
- Дисциплинирует разработчиков
- Отслеживание метрик в реальном времени
- Немедленный прогон тестов после каждого изменения
- Разгрузка машины разработчика

**Задачи CI сервера:**

- Генерация артефактов
- Прогон тестов
- Нотификация разработчиков о неудаче
- Сбор метрик (тестовое покрытие)
- Статический анализ кода
- Кросс-платформенная сборка

**CI/CD инструменты:**

- GitHub Actions
- GitLab CI
- Jenkins
- Travis CI
- CircleCI

### 3.10. GitHub Actions

**Пример workflow для Python:**

**yaml**

```
name: CI

on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main, develop ]

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python-version: ["3.10", "3.11"]

    steps:
    - uses: actions/checkout@v4

    - name: Set up Python
      uses: actions/setup-python@v5
      with:
        python-version: ${{ matrix.python-version }}

    - name: Install dependencies
      run: |
        pip install -r requirements.txt
        pip install pytest ruff mypy

    - name: Lint with ruff
      run: ruff check src/

    - name: Type check with mypy
      run: mypy src/

    - name: Test with pytest
      run: pytest tests/
```

## 4. Тестирование и Quality Assurance

### 4.1. Quality Assurance vs Тестирование

| QA                                                 | Тестирование                                     |
| -------------------------------------------------- | ------------------------------------------------ |
| Планируемая систематическая активность             | Целенаправленное исследование продукта           |
| Направлена на удовлетворение требований к качеству | Направлена на обнаружение и идентификацию ошибок |
| Проактивная (предотвращение)                       | Реактивная (обнаружение)                         |
| Весь процесс разработки                            | Конкретный этап                                  |

### 4.2. Классификация тестирования

**По знанию внутреннего устройства:**

- **Black box** — без знаний о внутреннем устройстве
- **White box** — с использованием знаний о внутреннем устройстве
- **Grey box** — комбинация

**По времени выполнения:**

- Статическое (без запуска кода)
- Динамическое (с запуском кода)

**По степени автоматизации:**

- Ручное
- Автоматическое

**По объекту тестирования:**

- Модульное (unit testing)
- Интеграционное (integration testing)
- Системное (system testing)
- Приёмочное (acceptance testing)

### 4.3. Статическое тестирование

Без запуска кода:

- Аудит кода (code review)
- Анализ кода инструментами

**Инструменты:**

| Язык       | Инструменты                |
| ---------- | -------------------------- |
| C/C++      | lint, PV-Studio            |
| Java       | FindBugs, Sonar, PMD       |
| Python     | ruff, pylint, flake8, mypy |
| JavaScript | JSlint, Closure compiler   |
| .NET       | FxCop, ReSharper           |

**Недостатки:**

- Много ложных срабатываний (false positives)
- Многие правила плохо соотносятся с конкретным проектом
- Сложно составить набор правил

### 4.4. Модульное тестирование (Unit Testing)

**Юнит-тест** — код, который тестирует код.

**python**

```
def sum(a, b):
    return a + b

def test_sum():
    assert sum(2, 2) == 4
```

**Преимущества:**

- Раннее обнаружение проблем
- Лёгкая встройка в сборку
- Облегчают регрессионное тестирование
- Удешевляют внесение изменений
- Упрощают интеграцию
- Улучшают низкоуровневую архитектуру

**Недостатки:**

- Требуют ресурсов (3–5 строк теста на строку кода)
- Требуют поддержки в актуальном состоянии
- Не обнаруживают проблемы интеграции
- Не обнаруживают ошибки в многопоточке
- Могут содержать ошибки

**Библиотеки:**

| Язык       | Инструменты         |
| ---------- | ------------------- |
| Java       | JUnit, TestNG       |
| Python     | pytest, unittest    |
| .NET       | NUnit               |
| JavaScript | Jest, Mocha         |
| C++        | Google Test, Catch2 |

### 4.5. Mock-объекты

**Mock-объект** — объект, моделирующий поведение внешнего окружения.

**Использование:** для изоляции тестируемого кода от внешних зависимостей (БД, сеть, файловая система).

**Библиотеки:** Mockito (Java), unittest.mock (Python), googlemock (C++)

### 4.6. Test-Driven Development (TDD)

**Цикл TDD:**

**text**

```
1. Написать тест (который заведомо не проходит)
2. Написать минимальный код для прохождения теста
3. Рефакторинг
4. Повтор
```

### 4.7. Тестовое покрытие

**Покрытие кода** — процент кода, выполняемый во время тестов.

**Метрики покрытия:**

- Statement coverage (покрытие операторов)
- Branch coverage (покрытие ветвей)
- Function coverage (покрытие функций)

**Инструменты:** coverage.py (Python), JaCoCo (Java), Istanbul (JavaScript)

### 4.8. Функциональное и интеграционное тестирование

Проверяют значительные части системы в сборе.

**Точки входа:**

- Внешнее API
- Внутреннее API
- Пользовательский интерфейс

**Инструменты:**

- Selenium (UI)
- REST Assured (API)
- Postman (API)

### 4.9. Тестирование производительности

**Нагрузочное тестирование (Load Testing):**

- Ответ на вопрос: справляется ли система с запланированной нагрузкой?

**Стресс-тестирование (Stress Testing):**

- Ответ на вопрос: с какой максимальной нагрузкой справится система?

**Необходимо:**

- Профиль нагрузки
- Инструмент для симуляции нагрузки
- Требования к системе под нагрузкой

**Метрики:**

- Среднее/максимальное/минимальное время ответа
- Загрузка процессора
- Использование памяти
- Процент необработанных запросов

**Инструменты:**

- JMeter
- LoadRunner
- k6
- wrk

## 5. Командные соглашения

### 5.1. Именование веток

**Формат:** `тип/номер-задачи-краткое-описание`

**Типы:**

- `feature/` — новая функциональность
- `bugfix/` — исправление ошибки
- `hotfix/` — срочное исправление
- `release/` — подготовка релиза

**Пример:**

**text**

```
feature/123-add-user-authentication
bugfix/456-fix-login-error
release/1.2.0
```

### 5.2. Соглашения по коммитам

**Формат (Conventional Commits):**

**text**

```
<type>(<scope>): <subject>

<body>

<footer>
```

**Типы:**

| Тип        | Описание               |
| ---------- | ---------------------- |
| `feat`     | Новая функциональность |
| `fix`      | Исправление ошибки     |
| `docs`     | Документация           |
| `style`    | Форматирование         |
| `refactor` | Рефакторинг            |
| `test`     | Тесты                  |
| `chore`    | Сборка, CI             |

**Пример:**

**text**

```
feat(auth): add JWT authentication

- Add JWT token generation
- Add token validation middleware

Closes #123
```

### 5.3. Шаблон Pull Request

**markdown**

```
## Описание изменений

[Краткое описание]

## Ссылка на задачу

[Ссылка на задачу в трекере]

## Тип изменений

- [ ] feat
- [ ] fix
- [ ] refactor
- [ ] docs
- [ ] test

## Чеклист

- [ ] Код соответствует стандартам
- [ ] Написаны тесты
- [ ] Тесты проходят
- [ ] Документация обновлена
- [ ] Проверена работа локально
```

### 5.4. Командные соглашения по ИИ

1. **Когда использовать:** для генерации тестов, рефакторинга, документации, поиска ошибок
2. **Какие инструменты:** ChatGPT, Copilot, Claude
3. **Верификация:** всегда проверять результат ИИ
4. **Документирование:** записывать промпты и оценку качества
5. **Ответственность:** за код отвечает разработчик

**Библиотека промпт-шаблонов:**

**markdown**

```
## Генерация тестов

**Промпт:**
Напиши pytest-тесты для функции:
[код функции]
Требования: покрыть все краевые случаи, использовать фикстуры.

## Рефакторинг

**Промпт:**
Проведи рефакторинг кода:
[код]
Цели: снизить сложность, улучшить читаемость, добавить аннотации типов.
```
