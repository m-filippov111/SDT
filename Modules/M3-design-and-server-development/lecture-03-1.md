**Лекция 3.1. Архитектура приложения и организация кода**

1\. Назначение

Сформировать у обучающихся понимание принципов построения архитектуры серверных приложений на Python, навыков организации кода в пакеты и модули, управления зависимостями и работы с виртуальными окружениями. Занятие закладывает основу для разработки серверной части командного проекта.

3\. Архитектура приложения: слои и компоненты

Архитектура приложения — это фундаментальная организация системы, определяющая её компоненты, их взаимосвязи и принципы взаимодействия. Для серверных приложений на Python наиболее распространена многослойная архитектура:

|     |
| --- |
| Presentation Layer<br><br>(User Interface)<br><br>FastAPI маршруты / обработчики |
| Application Layer<br><br>(Business Logic)<br><br>Сервисы / Use Cases / DTO |
| Domain Layer<br><br>(Domain Models / Entities)<br><br>Сущности / Value Objects / Aggregates |
| Infrastructure Layer<br><br>(Data Access / External APIs)<br><br>Репозитории / ORM / Клиенты API |

Ключевые принципы организации слоёв:

| Принцип | Описание |
| --- | --- |
| Разделение ответственности | Каждый слой отвечает за свою область: презентация — за взаимодействие с пользователем, бизнес-логика — за правила предметной области, инфраструктура — за внешние системы |
| Зависимости внутрь | Внешние слои зависят от внутренних, но не наоборот. Presentation → Application ← Infrastructure (инверсия зависимостей) |
| Слабые связи | Слои взаимодействуют через чёткие интерфейсы, что упрощает тестирование и замену компонентов |
| Тестируемость | Каждый слой можно тестировать изолированно (модульные тесты для бизнес-логики, интеграционные — для инфраструктуры) |

4\. Пакеты и модули в Python

Модуль — это файл с расширением .py, содержащий определения функций, классов и переменных.

Пакет — это директория, содержащая файл \__init_\_.py (может быть пустым) и другие модули/пакеты.

Правила организации кода:

python

project/

├── src/ _\# корневой пакет приложения_

│ ├── \__init_\_.py

│ ├── main.py _\# точка входа_

│ ├── api/ _\# API слой (презентация)_

│ │ ├── \__init_\_.py

│ │ ├── routes/ _\# маршруты FastAPI_

│ │ │ ├── \__init_\_.py

│ │ │ ├── users.py

│ │ │ └── products.py

│ │ └── schemas/ _\# Pydantic схемы (DTO)_

│ │ ├── \__init_\_.py

│ │ ├── user.py

│ │ └── product.py

│ ├── core/ _\# бизнес-логика (Application + Domain)_

│ │ ├── \__init_\_.py

│ │ ├── entities/ _\# доменные сущности_

│ │ │ ├── \__init_\_.py

│ │ │ ├── user.py

│ │ │ └── product.py

│ │ ├── services/ _\# сервисы (use cases)_

│ │ │ ├── \__init_\_.py

│ │ │ ├── user_service.py

│ │ │ └── product_service.py

│ │ └── interfaces/ _\# интерфейсы (абстракции)_

│ │ ├── \__init_\_.py

│ │ ├── user_repository.py

│ │ └── product_repository.py

│ └── infrastructure/ _\# инфраструктурный слой_

│ ├── \__init_\_.py

│ ├── database/ _\# работа с БД_

│ │ ├── \__init_\_.py

│ │ ├── models.py _\# SQLAlchemy модели_

│ │ └── repositories/ _\# реализация репозиториев_

│ │ ├── \__init_\_.py

│ │ ├── user_repository.py

│ │ └── product_repository.py

│ └── external/ _\# внешние API/сервисы_

│ ├── \__init_\_.py

│ └── payment_gateway.py

├── tests/ _\# тесты (зеркалируют структуру src/)_

│ ├── \__init_\_.py

│ ├── test_api/

│ ├── test_core/

│ └── test_infrastructure/

Соглашения по именованию:

- Модули — snake_case.py
- Пакеты — snake_case/
- Классы — PascalCase
- Функции/переменные — snake_case
- Константы — UPPER_SNAKE_CASE

5\. Управление зависимостями

Зависимость — это внешний пакет/библиотека, необходимый для работы вашего приложения.

Основные подходы к управлению зависимостями в Python:

| Инструмент | Назначение | Особенности |
| --- | --- | --- |
| pip + requirements.txt | Базовое управление | Простой, но требует ручного обновления версий |
| poetry | Современный менеджер | Автоматическое разрешение зависимостей, версионирование, публикация |
| pipenv | Альтернатива poetry | Объединяет pip и virtualenv |
| conda | Для научных вычислений | Управляет не только Python, но и системными библиотеками |

Структура requirements.txt:

txt

\# Основные зависимости

fastapi==0.104.1

uvicorn\[standard\]==0.24.0

sqlalchemy==2.0.23

alembic==1.12.1

pydantic==2.5.0

python-dotenv==1.0.0

\# Зависимости для разработки (dev)

pytest==7.4.3

ruff==0.1.6

mypy==1.7.0

pre-commit==3.5.0

Разделение зависимостей (практика):

- requirements.txt — основные зависимости
- requirements-dev.txt — зависимости для разработки (линтеры, тесты)

6\. Виртуальные окружения

Виртуальное окружение — это изолированная среда Python со своим собственным интерпретатором, библиотеками и путями.

Зачем нужно виртуальное окружение?

| Проблема | Решение |
| --- | --- |
| Разные проекты требуют разных версий одной библиотеки | Каждый проект получает свою изолированную среду |
| Установка пакетов глобально может конфликтовать с системными | Все зависимости устанавливаются локально в проект |
| Воспроизводимость окружения на других машинах | requirements.txt или poetry.lock фиксируют точные версии |

Инструменты для создания виртуальных окружений:

| Инструмент | Команда | Особенности |
| --- | --- | --- |
| venv (встроенный) | python -m venv .venv | Стандартный, лёгкий, подходит для большинства проектов |
| virtualenv | virtualenv .venv | Более старый, больше возможностей |
| poetry | poetry env use python3.10 | Автоматическое управление окружением |
| conda | conda create -n myenv python=3.10 | Для сложных проектов с системными зависимостями |

Работа с виртуальным окружением (venv):

bash

_\# Создание окружения_

python -m venv .venv

_\# Активация (Linux/macOS)_

source .venv/bin/activate

_\# Активация (Windows)_

.venv\\Scripts\\activate

_\# Установка зависимостей_

pip install -r requirements.txt

_\# Проверка установленных пакетов_

pip list

_\# Деактивация_

deactivate

Важно: директорию .venv следует добавить в .gitignore, чтобы не загружать виртуальное окружение в репозиторий.
