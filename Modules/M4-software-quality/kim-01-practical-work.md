# КИМ-4.1. Качество прикладного решения

## 1. Назначение

Проверить сформированность индикатора **PL-1.1** (уровень С): способность тестировать, отлаживать и оценивать качество прикладного решения на Python — покрыть ключевую логику командного проекта тестами, обеспечить их запуск в CI, применить практики логирования и диагностики, провести взаимное код-ревью между командами.

## 2. Проверяемые результаты обучения

| Код | Индикатор | Уровень | Дескриптор освоения |
| --- | --- | :---: | --- |
| PL-1.1 | Разрабатывает и отлаживает прикладные решения разной сложности с использованием Python, тестирует, испытывает и оценивает их качество | С | Обучающийся способен спроектировать набор модульных и интеграционных тестов для ключевой логики, обеспечить автоматический прогон в CI, использовать логирование и диагностику при поиске дефектов и оценить качество решения (своего и смежной команды) по наблюдаемым критериям |

## 3. Условия выполнения

| Параметр | Значение |
| --- | --- |
| **Форма контроля** | Текущая |
| **Время выполнения** | 2 недели (в рамках модуля 4, спринт 2) |
| **Формат сдачи** | Git-репозиторий команды |
| **Режим выполнения** | Групповой (3–5 человек); зоны ответственности по тестам и ревью закрепляются в матрице RACI |
| **Используемые инструменты** | Python 3, pytest, pytest-cov, FastAPI TestClient (или аналог), ruff/mypy (по CI модуля 2), logging, отладчик IDE/`pdb`, cProfile или эквивалент |
| **Допустимые источники** | Документация pytest, FastAPI, материалы лекций; код серверной части проекта (модуль 3) |
| **Правила использования ИИ** | Разрешено. Использование ИИ документируется в `ai-usage-log.md`; автор теста или исправления должен уметь объяснить сценарий, ожидаемый результат и причину правки |

## 4. Задание

Задание выполняется на **серверной части командного проекта** (результат спринта 1). Цель — сделать качество проверяемым: тесты, CI, логи, диагностика и взаимное ревью.

### Этап 1. План тестирования ключевой логики

В файле `docs/test-plan.md` опишите:

- какие модули / endpoint'ы / сценарии считаются **ключевой логикой** проекта (минимум 3 сценария предметной области);
- для каждого сценария — тип теста (модульный / интеграционный), входные данные, ожидаемый результат, критерий прохождения;
- какие риски не покрываются тестами осознанно (и почему).

### Этап 2. Модульные и интеграционные тесты (pytest)

Реализуйте тесты в каталоге `tests/`:

1. **Модульные тесты** — на чистую бизнес-логику (валидация, расчёты, преобразования) без подъёма всего сервера.
2. **Интеграционные тесты** — на HTTP API через TestClient (или аналог): успешный запрос, ошибка валидации, обращение к несуществующему ресурсу.
3. Используйте **фикстуры** для клиента API и тестовых данных (`conftest.py`).
4. Для ключевой логики обеспечьте минимум по одному тесту на:
   - корректные данные (счастливый путь);
   - граничный случай;
   - некорректные данные / ожидаемую ошибку.

### Этап 3. Покрытие и порог качества

1. Запускайте тесты с отчётом о покрытии: `pytest --cov=src --cov-report=term-missing`.
2. Зафиксируйте целевой порог покрытия **ключевых модулей** (рекомендуемый ориентир — не ниже 60% для модулей, перечисленных в плане; допустимо иное значение при обосновании в отчёте).
3. В `docs/quality-report.md` укажите фактическое покрытие и список файлов/веток, которые намеренно не покрыты.

### Этап 4. Тесты и линтеры в CI

Убедитесь, что CI-конвейер (настроенный в модуле 2) на каждом Pull Request:

- запускает линтер;
- запускает `pytest` (с покрытием);
- **падает** при провале тестов или линтера.

Приложите ссылку на успешный прогон CI для ветки спринта 2 (или скрин/лог job'а в `docs/quality-report.md`).

### Этап 5. Структурированное логирование

1. Введите единое соглашение по логированию (`docs/logging.md`): уровни, формат, что логируется на границах API и при ошибках.
2. В ключевые места серверной части добавьте записи лога (старт операции, успех/ошибка с контекстом без секретов).
3. Покажите на демонстрации, что по логу можно восстановить ход одного неуспешного запроса.

### Этап 6. Отладка и профилирование (минимум один кейс)

Оформите в `docs/quality-report.md` один диагностический кейс:

- **Отладка:** воспроизведённый дефект (упавший тест или сценарий) → локализация → исправление → регрессионный тест; **или**
- **Профилирование:** измерение «до» → найденное узкое место → правка → измерение «после».

Кейс должен быть проверяемым: есть ссылка на коммит/PR и краткие числа или стек/фрагмент лога.

### Этап 7. Автодокументация API (обзорно)

1. Проверьте, что OpenAPI UI (`/docs` или `/redoc`) открывается для приложения.
2. Для endpoint'ов ключевой логики укажите краткие описания и модели ответов (чтобы схема отражала реальное поведение).
3. В `docs/quality-report.md` дайте ссылку/скрин и перечислите покрытые схемой операции.

### Этап 8. Код-ревью между командами

По регламенту преподавателя каждая команда:

1. Выбирает один Pull Request или согласованный участок кода **другой** команды.
2. Проводит ревью по чеклисту: читаемость, тесты, обработка ошибок, логирование, соответствие критериям приёмки.
3. Фиксирует замечания и ответы авторов в `docs/cross-team-review.md` (у обеих команд — свой протокол со ссылкой на ревьюируемый репозиторий/PR).
4. По собственным замечаниям (если ревьюили вас) вносит правки или обосновывает отказ.

### Чеклист приёмки

Работа принимается, когда выполнены все пункты. Это же список проверяет преподаватель и ориентир для спринт-ревью 2.

- [ ] В `docs/test-plan.md` описаны ключевые сценарии, типы тестов и ожидаемые результаты.
- [ ] Есть модульные и интеграционные тесты; используются фикстуры.
- [ ] Для ключевой логики есть тесты на корректные, граничные и некорректные данные.
- [ ] `pytest` проходит локально; отчёт о покрытии сохранён/отражён в `docs/quality-report.md`.
- [ ] CI запускает линтер и тесты и падает при ошибках; есть свидетельство успешного прогона.
- [ ] Действует соглашение по логированию; по логу восстанавливается ход ошибочного запроса.
- [ ] Оформлен минимум один кейс отладки или профилирования с измеримым/проверяемым результатом.
- [ ] OpenAPI UI доступен; ключевые endpoint'ы описаны.
- [ ] Заполнен протокол `docs/cross-team-review.md` с конкретными замечаниями и статусом правок.
- [ ] Файлы размещены по структуре из раздела «Формат сдачи».

## 5. Формат сдачи

```text
team-XX-project/
├── docs/
│   ├── test-plan.md           # план тестирования
│   ├── quality-report.md      # покрытие, CI, диагностика, OpenAPI
│   ├── logging.md             # соглашение по логированию
│   ├── cross-team-review.md   # протокол межкомандного ревью
│   └── ai-usage-log.md        # логи работы с ИИ
├── src/                       # серверная часть (модуль 3) + правки по качеству
├── tests/
│   ├── conftest.py            # фикстуры
│   ├── test_*.py              # модульные и интеграционные тесты
│   └── ...
├── pytest.ini                 # или pyproject.toml с настройками pytest
└── .github/workflows/         # CI с линтером и pytest (модуль 2)
```

## 6. Критерии оценивания

Баллы за критерий выставляются по чеклисту приёмки: полностью закрытые пункты критерия — верхняя граница веса, частично — середина, не закрыты — ноль.

| № | Критерий | Вес | Проверяемые пункты чеклиста |
| --- | --- | :---: | --- |
| 1 | План тестирования | 10% | Ключевые сценарии и ожидаемые результаты описаны |
| 2 | Модульные и интеграционные тесты | 25% | Есть оба уровня, фикстуры, сценарии корректных/граничных/ошибочных данных |
| 3 | Покрытие и отчёт о качестве | 15% | Покрытие измерено, порог/исключения обоснованы в отчёте |
| 4 | CI с тестами и линтером | 15% | CI реально гоняет проверки и блокирует провалы |
| 5 | Логирование и диагностика | 15% | Соглашение по логам + кейс отладки или профилирования |
| 6 | Документация API (OpenAPI) | 5% | UI доступен, ключевые операции описаны |
| 7 | Код-ревью между командами | 15% | Протокол с конкретными замечаниями и статусом правок |

Оформление репозитория (структура, читаемость документации) учитывается в пределах критериев 1–7.

## 7. Шкала оценивания

| Уровень | Диапазон баллов | Характеристика |
| --- | :---: | --- |
| Средний | 60–79% | Тесты и CI есть, но часть пунктов чеклиста не закрыта (слабы граничные сценарии, диагностика или межкомандное ревью) |
| Средний + | 80–89% | Закрыты все ключевые пункты: осмысленные тесты, зелёный CI с реальными проверками, логирование и протокол ревью |
| Средний ++ | 90–100% | Закрыт весь чеклист: план и отчёт согласованы, диагностика с измеряемым эффектом, содержательное межкомандное ревью |
| Ниже среднего | < 60% | Тесты формальны или не связаны с проектным кодом; CI не гоняет проверки; ревью отсутствует |

## 8. Методические рекомендации

### Для студентов

1. **Сначала план — потом тесты.** Список ключевых сценариев из `test-plan.md` должен совпадать с тем, что реально лежит в `tests/`.
2. **Красный тест полезнее зелёного «пустого».** Начните с падающего теста на известный дефект или на новый критерий приёмки.
3. **Покрытие — индикатор, не фетиш.** Лучше 60% на критичной логике, чем 90% на геттерах.
4. **ИИ пишет тест — вы отвечаете за смысл.** На защите и ревью вас спросят, что именно проверяет тест и почему ожидание такое.
5. **Межкомандное ревью** оценивается по качеству замечаний: «переименуйте», «добавьте тест на 404», «в лог уходит токен» — лучше, чем «всё хорошо».

### Для преподавателей

1. Проверяйте работу по чеклисту приёмки — он же основа демонстрации на спринт-ревью 2.
2. Запросите прогон `pytest` и открытие отчёта CI в присутствии команды.
3. Задайте автору 1–2 вопроса по его тестам (по истории репозитория).
4. Сверьте парность межкомандного ревью: у команды A есть протокол по B и наоборот (по назначению пар).
5. Убедитесь, что тесты бьют по коду проекта, а не по учебному примеру из лекции.

## 9. Пример выполнения

> **Проект**: «Система мониторинга успеваемости студентов».
>
> **Ключевая логика**: создание оценки, расчёт среднего балла по дисциплине, выдача 404 при отсутствии студента.
>
> **Тесты**: `test_grades.py` — модульные на расчёт среднего (обычный, пустой список, отрицательная оценка); `test_api_grades.py` — интеграционные через TestClient (201 на создание, 422 на невалидное тело, 404 на неизвестный id).
>
> **Покрытие**: `src/services/grades.py` и `src/api/grades.py` — 78%; миграции и скрипты сидов исключены осознанно.
>
> **CI**: job `test` гоняет `ruff` и `pytest --cov=src`; PR без тестов на новый endpoint не проходит review checklist.
>
> **Логи**: при 422 пишется WARNING с `request_id` и кодом ошибки без тела паролей.
>
> **Диагностика**: N+1 при списке оценок — до 1.8 с на 200 записей, после `selectinload` — 0.2 с; закреплён интеграционным тестом на число SQL (или зафиксировано в отчёте замером).
>
> **Межкомандное ревью**: команде-партнёру указано отсутствие теста на 409 при дубликате; замечание принято, тест добавлен в follow-up PR.
