# Лекция 4. Качество программного обеспечения

Лекция носит установочный характер: она задаёт рамку для лабораторных работ модуля и второго спринта проекта, а не заменяет документацию pytest или отладчика. Цель — научиться **тестировать, отлаживать и оценивать качество** прикладного решения на Python (PL-1.1, уровень С) в условиях командного проекта.

## 1. Что значит «качество» в прикладном решении

Качество — не отдельный этап «в конце», а набор наблюдаемых свойств работающего продукта:

- **корректность** — код делает то, что обещают требования и критерии приёмки;
- **устойчивость** — ошибки обрабатываются осознанно, а не роняют сервис;
- **наблюдаемость** — по логам и диагностике можно понять, что произошло;
- **поддерживаемость** — изменения проверяются автоматически и не ломают уже работающее;
- **прозрачность** — API и поведение документированы настолько, чтобы ими могли пользоваться другие.

Ключевая мысль модуля: качество проверяется **артефактами в репозитории** (тесты, CI, логи, отчёты ревью), а не заявлениями в презентации.

## 2. Тестирование на Python (занятие 4.1)

### 2.1. Уровни тестов

| Уровень | Что проверяет | Типичный инструмент |
| --- | --- | --- |
| Модульный | Отдельную функцию / класс в изоляции | `pytest` |
| Интеграционный | Взаимодействие слоёв (API ↔ сервис ↔ БД) | `pytest` + TestClient / тестовая БД |
| Регрессионный | Что уже работавшее не сломалось после изменений | набор ранее написанных тестов в CI |

Для учебного проекта достаточно осмысленного сочетания модульных и интеграционных тестов по **ключевой логике** предметной области — не «100% строк ради процента».

### 2.2. pytest: базовые практики

- тесты живут в `tests/`, имена файлов и функций — `test_*.py` / `test_*`;
- один тест проверяет один сценарий (корректный, граничный или ошибочный);
- **фикстуры** (`@pytest.fixture`) готовят повторяемое окружение: клиент API, тестовые данные, временную БД;
- **параметризация** (`@pytest.mark.parametrize`) удобна для набора входных значений без копирования кода;
- утверждения через `assert` должны быть читаемыми: при падении видно, что ожидалось и что получено.

### 2.3. Покрытие и линтеры

- **Покрытие** (`pytest-cov`) показывает, какие ветки кода исполнялись тестами. Порог покрытия — ориентир, а не цель сама по себе: важнее покрыть критичные сценарии (создание сущности, валидация, ошибочный ввод, ключевой расчёт).
- **Линтеры** (`ruff` / `flake8`) и проверки типов (`mypy`, обзорно) ловят целый класс дефектов до запуска. В модуле 2 CI уже настроен — здесь задача **наполнить** конвейер реальными тестами проекта и убедиться, что красный CI блокирует слияние.

### 2.4. Тесты в CI

Хороший CI для модуля 4:

1. устанавливает зависимости;
2. запускает линтер;
3. запускает `pytest` с отчётом о покрытии;
4. падает, если тесты или линтер не прошли.

Зелёный CI на пустом наборе тестов не считается достижением: проверяется связка «код проекта → тесты → автоматический прогон».

## 3. Отладка, логирование и профилирование (занятие 4.2)

### 3.1. Отладка

Отладчик (IDE или `pdb`/`breakpoint()`) нужен, когда тест или ручной сценарий воспроизводят дефект. Полезный порядок:

1. воспроизвести ошибку минимальным сценарием (лучше — упавшим тестом);
2. локализовать место (стек, лог, точка останова);
3. исправить причину, а не симптом;
4. закрепить исправление регрессионным тестом.

### 3.2. Структурированное логирование

`print` для диагностики серверного приложения недостаточен. Практики модуля:

- модуль `logging` с уровнями (DEBUG / INFO / WARNING / ERROR);
- единый формат записи (время, уровень, модуль, сообщение; при необходимости — `request_id`);
- логирование границ важных операций и ошибок с контекстом;
- секреты и персональные данные в лог не пишутся.

Соглашение команды фиксируется в `docs/logging.md` (шаблон — `attachments/logging-template.md`).

### 3.3. Профилирование

Профилирование ищет **узкие места**, а не «ускоряет всё подряд»:

- измерить (например, `cProfile`, простые таймеры, логи длительности запросов);
- найти доминирующую операцию (часто — N+1 к БД, лишние преобразования, синхронный тяжёлый код на пути запроса);
- улучшить точечно и повторно измерить.

В учебном проекте достаточно одного документированного кейса: «было медленно / измерили / причина / что сделали / стало».

### 3.4. Автогенерируемая документация API (обзорно)

FastAPI отдаёт OpenAPI-схему (`/docs`, `/redoc`). Для качества это:

- контракт для клиентов и для интеграционных тестов;
- проверка, что endpoint'ы описаны (summary, коды ответов, модели);
- способ быстро показать поведение системы на спринт-ревью без отдельных слайдов «про API».

## 4. Оценка качества и взаимное код-ревью

Оценка качества в модуле — это короткий отчёт команды: что покрыто тестами, какой порог покрытия достигнут, что показал CI, какие дефекты найдены на ревью, что улучшено по логам/профилю.

**Код-ревью между командами** (СРС модуля 4) дополняет внутреннее ревью модуля 2:

- команда A ревьюит выбранный Pull Request / участок кода команды B и наоборот;
- замечания конкретны (что не так, почему, как проверить исправление);
- итог фиксируется в протоколе (шаблон — `attachments/cross-team-review-template.md`).

Так PL-1.1 отрабатывается не только «написать тесты», но и **испытать и оценить** чужое решение по понятным критериям.

## 5. Типичные ошибки

- Тесты только на «счастливый путь», без граничных и ошибочных сценариев.
- Погоня за процентом покрытия вместо покрытия ключевой бизнес-логики.
- CI зелёный, потому что тестов почти нет или они не запускаются.
- Логи без контекста или с секретами; отладка «вслепую» без воспроизводимого сценария.
- Профилирование без измерения «до/после».
- Межкомандное ревью формальное («всё ок») без проверяемых замечаний.

## 6. Связь с проектом

Материал модуля реализуется во **втором спринте**: команда покрывает тестами ключевую логику серверной части (результат спринта 1), добивается прохождения CI, проводит код-ревью между командами и показывает это на спринт-ревью 2. Подробности — в [КИМ-4.1](kim-01-practical-work.md).
