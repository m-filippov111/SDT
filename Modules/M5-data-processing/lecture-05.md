# Лекция 5. Обработка данных в приложении

Лекция носит установочный характер: она задаёт рамку для лабораторных работ модуля и третьего спринта проекта, а не заменяет документацию библиотек. Цель — научиться **обоснованно выбирать** инструменты обработки данных (PL-1.2) и **строить простой конвейер** обработки данных (PL-1.3), встроенный в приложение.

## 1. Данные в приложении

Почти любое прикладное решение работает с данными: принимает их на вход, преобразует и отдаёт результат. Типичные задачи подсистемы данных:

- собрать данные из источника (файл, внешний сервис, база данных);
- привести их к пригодному для работы виду (очистка, приведение типов, объединение);
- рассчитать показатели и сформировать отчётную выборку;
- отдать результат пользователю или другой части системы.

Ключевая мысль модуля: подсистема данных — **часть работающего приложения**, а не отдельный разовый скрипт.

## 2. Выбор инструментов обработки и визуализации (PL-1.2)

### 2.1. Обзор типовых библиотек

- **NumPy** — эффективные операции над числовыми массивами; основа для вычислений.
- **Pandas** — работа с табличными данными: чтение/запись, фильтрация, группировки, агрегация, обработка пропусков.
- **Matplotlib** — построение графиков и визуализаций для отчётов.

Это распространённый, но не единственный набор: под конкретную задачу могут подойти другие инструменты.

### 2.2. Как обосновывать выбор

Выбор оценивается **не по названию библиотеки, а по обоснованию**. Полезно опираться на явные критерии:

- пригодность под тип и объём данных;
- производительность под требования задачи;
- читаемость и поддерживаемость кода;
- простота интеграции с приложением;
- зрелость инструмента и качество документации.

Хорошее обоснование сравнивает минимум две альтернативы по этим критериям и делает вывод под требования проекта (шаблон — `attachments/library-choice-template.md`).

## 3. Конвейеры обработки данных (PL-1.3)

### 3.1. Схема ETL

Простой конвейер удобно разбивать на три шага:

```text
Extract → Transform → Load
(извлечение) (преобразование) (загрузка)
```

- **Extract** — получить данные из источника и проверить их пригодность.
- **Transform** — очистить, преобразовать, рассчитать показатели.
- **Load** — сохранить результат в хранилище или отдать приложению.

Разделение на шаги делает конвейер понятным, тестируемым и переиспользуемым.

### 3.2. Свойства хорошего конвейера

- **Обработка ошибок.** «Грязные» данные (пропуски, неверные типы, пустой вход) не должны ронять весь конвейер: ошибочные записи логируются и обрабатываются осознанно.
- **Логирование.** Ключевые шаги и ошибки фиксируются в логе — это основа для диагностики.
- **Масштаб данных.** Если вход не помещается в память, данные читают частями (`pd.read_csv(chunksize=...)` или итеративно) и обрабатывают порциями — так конвейер не зависит от размера файла.
- **Идемпотентность.** Повторный запуск на тех же данных не создаёт дублей. При загрузке в СУБД это обеспечивают ключом идемпотентности: естественный ключ записи + `UPSERT` (`INSERT ... ON CONFLICT ...`) либо очистка целевой выборки перед загрузкой; простой `INSERT` на втором прогоне даст дубли.
- **Воспроизводимый запуск.** Конвейер запускается одной понятной командой по документированному регламенту (шаблон — `attachments/pipeline-template.md`).

### 3.3. Тестирование преобразований

Логику преобразований полезно покрывать тестами: на корректных данных, на граничных случаях и на некорректных данных (проверка обработки ошибок). Так изменения в конвейере не ломают уже работающие расчёты.

## 4. Интеграция подсистемы данных в приложение

Результат конвейера должен быть доступен пользователю, а не лежать локальным файлом «в столе». Типовой приём — отдавать отчётную выборку или визуализацию через endpoint серверной части (например, `GET /reports/...` на FastAPI из модуля 3). Так подсистема данных становится частью пользовательского сценария.

## 5. Типичные ошибки

- Выбор библиотеки «по привычке» без сопоставления с требованиями.
- Один большой скрипт без разделения на extract/transform/load.
- Отсутствие обработки ошибок: первый же некорректный ввод роняет конвейер.
- Результат не интегрирован в приложение.
- Нет тестов — любое изменение рискует незаметно сломать расчёты.
